# Mechanical Pre-Commit Hook Reference

> Reference documentation for the Git pre-commit hook generated by `.agents/scripts/install-hooks.sh`. This file describes behaviour only. It documents the hook exactly as it ships today, plus the known limits and maintenance items that follow from that behaviour.

The pre-commit hook is the mechanical half of the Dev-OS commit gate. The scripted half is `.agents/scripts/commit.sh`, which collects human approval and exports the approval token. The hook is what physically stops a commit when the token is absent or when Gitleaks finds a secret in the staged diff.

---

## 1. Installation

```bash
./.agents/scripts/install-hooks.sh
```

The installer:

1. Resolves the repository root with `git rev-parse --show-toplevel`, and exits `1` with `[ FAIL ]` if the working directory is not inside a Git repository.
2. Creates `.git/hooks/` if it does not exist.
3. Backs up an existing `pre-commit` hook **only when that hook does not already contain the string `DEVOS_COMMIT_APPROVED`**. The backup path is `.git/hooks/pre-commit.backup.<YYYYMMDDHHMMSS>` and a `[ WARN ]` line reports it. A hook that already contains the marker is treated as a Dev-OS hook and is overwritten in place without a backup.
4. Writes the hook body from a quoted heredoc (`<< 'EOF'`), so nothing in the template is expanded at install time — every variable in the hook is evaluated when the hook runs.
5. Runs `chmod +x` on the hook and prints the install path.

`devos init` chmods `install-hooks.sh` but does **not** run it. `devos doctor` reports a missing `.git/hooks/pre-commit` as an optional `[ WARN ]` check, not a failure.

## 2. What the Generated Hook Does

The hook runs two stages in order and exits `0` only if both pass.

```
git commit
   │
   ▼
.git/hooks/pre-commit
   │
   ├── 1. Commit gate: is DEVOS_COMMIT_APPROVED == "true"?
   │      ↳ No  : [ FAIL ] exit 1  ("Direct 'git commit' is disabled by policy")
   │      ↳ Yes : continue
   │
   └── 2. Secret scan: is `gitleaks` on PATH?
          ↳ No  : [ WARN ] print install hint, skip the scan, continue
          ↳ Yes : run the scan against the staged diff
                    ↳ Leaks found : [ FAIL ] exit 1  ("Hardcoded secret detected")
                    ↳ Clean       : [ OK ] "Secret scan clean."
   │
   ▼
[ OK ] Dev-OS pre-commit checks passed.  exit 0
```

### Stage 1 — The commit gate

The hook tests `$DEVOS_COMMIT_APPROVED` against the literal string `true`. Any other value, including an unset variable, aborts the commit with exit status `1` and points the caller at `.agents/scripts/commit.sh`. The failure message also states that exporting `DEVOS_COMMIT_APPROVED=true` is acceptable for an authorized automated pipeline.

`commit.sh` satisfies this stage by exporting the variable immediately before it calls `git commit`. The export lives in the script's own shell, so it applies to that one commit and does not leak into the interactive session.

The token is a policy control, not a security boundary. It is trivially exportable by anyone who reads the failure message. Its purpose is to make raw `git commit` an explicit, deliberate act rather than a default one — which is precisely the failure mode recorded in [LESSONS.md](LESSONS.md) under "Hardcoded Secret Leaked in PR".

### Stage 2 — Secret Scanning (Gitleaks & Built-in Engine)

Dev-OS treats secret scanning as a mandatory automated gate. `devos init` and `devos update` automatically detect, install, or update Gitleaks out of the box (via Homebrew, Snap, or direct binary download into `.agents/bin/gitleaks`).

1. **Gitleaks Scanning:** If `gitleaks` is available on the system PATH or in `.agents/bin/gitleaks`, the hook executes:
   ```bash
   gitleaks git --staged --verbose
   ```
   If a secret or credential is found, the commit is aborted with exit code `1`.

2. **Built-in Zero-Dependency Scanner:** If Gitleaks cannot be installed (e.g. airgapped offline environments), the pre-commit hook automatically falls back to an embedded high-precision regular expression scanner covering AWS access keys, GitHub tokens, OpenAI keys, Anthropic keys, Google API keys, Slack tokens, and PEM private keys.

Secret scanning is never skipped, and no manual package installation is required by the user.

## 3. Where the Hook Lives, and Automated Provisioning

The hook is written to `.git/hooks/pre-commit`.

Key architectural properties:
- **Zero Manual Steps:** `devos init` automatically initializes the git repository if missing and provisions `.git/hooks/pre-commit` during project setup.
- **Continuous Maintenance:** Running `devos update` re-verifies hook permissions and checks for Gitleaks binary updates.
- **Safety Backups:** If an existing non-Dev-OS pre-commit hook is present, `install-hooks.sh` preserves it by creating a timestamped backup before writing the Dev-OS gate.
- **Bypass Prevention:** Raw `git commit` is blocked without QA approval via `.agents/scripts/commit.sh` or explicit pipeline approval (`DEVOS_COMMIT_APPROVED=true`).

## 4. Known Issues

Two items were raised against the hook template. Both were checked against the source at `.agents/scripts/install-hooks.sh` and against a live Gitleaks install (8.30.1, Homebrew, macOS). One is confirmed; one did not reproduce. Both are recorded here, including the one that did not reproduce, so the question is not re-opened from memory later.

### Issue 1 — The hook calls a legacy Gitleaks subcommand (RESOLVED in v2.1.0)

The generated hook previously ran:

```bash
gitleaks protect --staged --verbose
```

`protect` is a legacy subcommand. On Gitleaks 8.30.1+ it no longer appears in the `Available Commands` list printed by `gitleaks --help`. In Dev-OS v2.1.0, this invocation was updated in `.agents/scripts/install-hooks.sh` to the documented current form:

```bash
gitleaks git --staged --verbose
```

### Issue 2 — Fragile `$?` testing between commands (HARDENED in v2.1.0)

Testing `$?` on a later line is a fragile idiom: inserting an echo or log line can reset `$?` and silently bypass failure handling. In Dev-OS v2.1.0, this was hardened to test the command directly:

```bash
if ! gitleaks git --staged --verbose; then
    echo ""
    echo "[ FAIL ] GITLEAKS ERROR: Hardcoded secret or API key detected in staged files."
    echo "[ WARN ] Commit aborted to prevent secret leak."
    echo ""
    exit 1
fi
```

This eliminates the ordering hazard completely.

## 5. Verifying the Gate Yourself

The gate is worth verifying per machine, since installation is manual and Gitleaks is optional. In a scratch repository:

```bash
git init /tmp/hook-check && cd /tmp/hook-check
/path/to/dev-os/.agents/scripts/install-hooks.sh

# Stage 1: the commit gate should abort with [ FAIL ] and exit 1.
git commit --allow-empty -m "should be blocked"

# Stage 2: the secret scan should abort with [ FAIL ] and exit 1.
printf 'AWS_KEY = "AKIAIMNOJVGFDXXXE4OA"\n' > leak.txt
git add leak.txt
DEVOS_COMMIT_APPROVED=true git commit -m "should also be blocked"

git log --oneline   # expect no commits
```

If the second command succeeds, check `gitleaks version` first — a missing binary makes the hook warn and continue rather than scan.
